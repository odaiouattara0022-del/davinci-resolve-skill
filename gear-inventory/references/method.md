# Method: how to run an inventory that stays true

The software is the easy part. Inventories fail for three reasons: entering
gear is slow, returning gear is optional, and nobody ever counts. Everything
below is aimed at those three.

## 1. Tag scheme

`CATEGORY-NNNN`, four digits, generated by `add` when you omit `--tag`:
`CAM-0001`, `LENS-0042`, `BAT-0007`.

- **Keep categories short and few.** Ten to twenty for a production fleet:
  `CAM LENS AUDIO LIGHT GRIP MEDIA BAT CABLE POWER MONITOR DRONE CASE COMPUTER`.
  Sub-types belong in `name` and `model`, not in the tag.
- **Never reuse a number**, even after retiring an asset. The history and the
  old printed labels still refer to it.
- **Tags are not serial numbers.** Serial goes in `serial`, is unique in the
  database, and is what insurance and police reports need.
- If you already have an internal numbering scheme, keep it: pass `--tag`
  explicitly or put it in the CSV's `tag` column.

## 2. Ownership: personal and professional in one database

Use `owner` as the hard divider - `PERSO` versus the company entity - and never
mix it with `holder` (who currently has the thing) or `location`.

```bash
python3 scripts/inventory.py ls --owner PERSO
python3 scripts/inventory.py report by owner
python3 scripts/inventory.py export --owner STUDIO --out studio-insurance.csv
```

This is what lets one database answer both "what do I personally own" (tax,
insurance, resale) and "what is the company's" (depreciation, the policy
schedule) without keeping two lists that disagree.

## 3. Getting the gear in

For anything over ~30 items, do not type them one by one:

1. `python3 scripts/inventory.py template --out gear.csv`
2. Fill it in a spreadsheet - or paste in an export from whatever you use now.
3. `import gear.csv --dry-run`, fix what it complains about, then `import gear.csv`.

Fill `name`, `category`, `owner`, `location`, `serial` and `purchase_price`
first. Everything else can be added later with `set`. A half-filled inventory
that exists beats a perfect one you never finish.

Photograph serial plates as you go; the database stores the number, and the
photos live in a folder named after the tag.

## 4. Movement discipline

The single rule that decides whether the inventory survives: **gear leaves the
shelf only through `checkout`, and comes back only through `checkin`.**

Make it fast enough that people comply:

```bash
# a USB barcode reader types straight into stdin
python3 scripts/inventory.py scan --mode checkout --to alice --days 3 --project "Spot Nike"
python3 scripts/inventory.py scan --mode checkin --at SHELF-A
```

Always set a `--due` or `--days` on a check-out. Without it `out --overdue`
has nothing to report, and gear quietly disappears into someone's car.

Use `kit` for anything that always travels together (body + lenses + batteries
+ media). One command instead of fifteen, and `kit checkout` refuses to go out
incomplete unless you pass `--partial`.

## 5. Counting: the audit

A stocktake is the only thing that finds theft, loss and clerical drift.

```bash
python3 scripts/inventory.py audit new 2026Q3-SHELFA --scope location=SHELF-A
python3 scripts/inventory.py scan --mode audit --audit 2026Q3-SHELFA
python3 scripts/inventory.py audit report 2026Q3-SHELFA
```

The report classifies every difference:

| Result | Means |
|--------|-------|
| `MISSING` | the books say it is here, it was not scanned - look for it |
| `UNEXPECTED` | scanned here, recorded somewhere else - `move` it |
| `PRESENT BUT LOGGED OUT` | returned without a check-in - fix the habit |
| `OUT (with alice)` | legitimately out, not expected on the shelf |

Read the report, chase the discrepancies, *then* `audit report --close`, which
marks whatever is still missing as `lost`.

**Cadence:** small kit, twice a year. Working fleet, one location per month on
rotation plus a full count annually. High-value or high-churn gear, count after
every big job. Scope each audit to one location - a whole-fleet audit that
takes a day never gets done.

## 6. Upkeep, in ten minutes a week

```bash
python3 scripts/inventory.py out --overdue      # chase late returns
python3 scripts/inventory.py stock low          # reorder before the shoot
python3 scripts/inventory.py maint due --days 30
python3 scripts/inventory.py report summary
```

Set `maint_interval_days` on anything with a service life - sensor cleans,
battery health checks, jib greasing, PAT/electrical tests - and the fleet tells
you what is due instead of you remembering.

## 7. Backups and history

The whole inventory is one file. Two workable patterns:

- **Git** (recommended for one operator): keep the `.db` in a private repo and
  commit after each session. `git log` then doubles as a point-in-time record.
- **Snapshot before anything bulk**: `cp inventory.db inventory-$(date +%F).db`
  before an import, a mass edit, or closing an audit.

Also export a flat CSV periodically - `export --out inventory-$(date +%F).csv`.
It is what your insurer, your accountant and any future tool will ask for, and
it is readable in fifty years.

## 8. What changes at scale

| Fleet size | What to change |
|-----------|----------------|
| < 100 | Nothing. Tags, check-out, one audit a year. |
| 100-500 | A barcode reader (`scan` mode). Kits. Scoped monthly audits. |
| 500-5,000 | Locations down to shelf/case level. A named person owning the data. Weekly `out --overdue`. Consider RFID for stocktakes. |
| > 5,000 | Multi-user writes and a phone app for the crew become the bottleneck, not the data model - see [tool-comparison.md](tool-comparison.md) and plan the migration via `export`. |

The data model does not change as you grow; the *discipline* does. Every item
above is a habit, not a feature.
